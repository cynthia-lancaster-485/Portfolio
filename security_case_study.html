Learning to build securely by breaking things.

A university security course where I spent a semester attacking systems the way an adversary would: exploiting web apps, breaking cryptography, sniffing network traffic, and then building the defenses that catch those same attacks. It is the clearest reason I design software with an attacker's mindset.

Why it matters to my work

The best way to write secure code is to know how it breaks.

In my full stack work I care a lot about getting security right: role based access enforced on the server, uploads validated by their actual contents, forms that hold up against crafted requests. This course is where that instinct comes from. Once you have written the exploit for an injection flaw or a weak token yourself, you never build the vulnerable version again, and you spot it quickly in code review.

Below is a high level tour of what I worked on. I am deliberately not sharing the exploit code or step by step attacks (see the note at the end).

What I worked on

Four areas, offense and defense.

🌐
Web application security

Exploiting the OWASP Top 10

Hands on work with the most common classes of web vulnerability, attacking a deliberately vulnerable application to understand exactly how each one works.

  • SQL injection, including automating the discovery of injectable inputs
  • Cross-site scripting (XSS)
  • Cross-site request forgery (CSRF)
🔑
Applied cryptography

Breaking real cryptographic schemes

The toughest part of the course: attacking cryptography not by guessing keys, but by exploiting how the schemes are built and used.

  • An RSA padding oracle attack (Bleichenbacher)
  • A hash length extension attack to forge a signed request
  • Hash collisions, and classical cryptanalysis using letter frequency and chi-squared analysis
📡
Network security

Reading what crosses the wire

Parsing raw network traffic to see what older, cleartext protocols leak, and why encryption in transit matters.

  • Packet parsing from scratch
  • Capturing credentials sent in the clear (for example FTP and IMAP)
🛡️
Detection and defense

Catching the attack, not just launching it

For every network attack, I also built the detection side: watching a stream of traffic and flagging the malicious pattern. Thinking about both halves is what made the ideas stick.

  • Signature and anomaly style detection of the attacks above

What I took away

Security is a way of thinking, not a checklist.

01

Trust nothing from the outside

Every input, header, token, and file is something an attacker controls. I validate on the server, because that is the only place a control actually holds.

02

Crypto fails at the edges

The attacks rarely break the math. They exploit padding, reuse, and how a scheme is wired into an app. That shapes how carefully I treat tokens and sessions.

03

Defense needs the attacker's view

Building detection right after the attack taught me that you can only defend what you understand how to break.

A note on why there's no code here

This was an offensive security course, so the deliverables were working exploits against a target environment built for the class. I keep that code private, out of respect for academic integrity (these assignments are reused) and good security practice (working exploits should not be posted publicly). I am always happy to talk through the concepts and my approach in an interview.
